# Coaching tools exist; durable local coaching does not

The claim that nothing does longitudinal coaching is true of the three tools the proposal names and false of the field: at least nine tools and two vendor features already analyse coding-agent sessions across time, and four of them call themselves coaches. What none of them combines is hook-time observation, deterministic findings with stable identifiers, a durable local record that holds no prompt text, and an optional metered model pass, which is the combination the agent-caddie design already describes. The proposal under review agrees with that design on its overall shape (a cheap synchronous path, a detached pass after the session, one tip at the next session start) and conflicts with it on four points: it stores raw prompt text, it uses SQLite, it relies on "the user's existing auth", and it adds work on the prompt path. Of its five metrics, verification and grounding have vendor backing and indirect empirical support, the correction ratio and the context-drift score need reframing because their base rates and thresholds do not survive the published data, and the micromanagement index has no supporting evidence and some against it. The field evidence is strongest on what breaks: SQLite written from concurrent hooks, daemons started from hooks, background model calls on a subscription, and model judgements made without enough context. ADR-0018 has twelve decisions to make; this report sets out the options and evidence for each and does not choose. No study or tool shows that coaching of this kind changes developer behaviour, so every option carries that uncertainty.

## The gap claim holds for the three named tools and fails for the field

The three tools the proposal names are per-prompt tools, as it says. **The Anthropic Console Prompt Improver rewrites one prompt template in a web console and has no notion of a session** ([Anthropic](https://www.anthropic.com/news/prompt-improver)). `severity1/claude-code-prompt-improver`, the popular plugin with that name (1,973 stars), hooks `UserPromptSubmit` and has the main session model ask one to six clarifying questions; it makes no separate model call and keeps no state ([README](https://raw.githubusercontent.com/severity1/claude-code-prompt-improver/main/README.md)). The repository whose name matches the proposal exactly, `GaZmagik/claude-prompt-improver`, has four stars ([GitHub](https://github.com/GaZmagik/claude-prompt-improver)). PrompyAI is an MCP server that scores a prompt from 0 to 100 on four dimensions with a rule-based scorer, calls Haiku for a rewrite when `ANTHROPIC_API_KEY` is set, and ships telemetry that is on by default ([README](https://raw.githubusercontent.com/samouh-waleed/prompyai/HEAD/README.md), [telemetry source](https://github.com/samouh-waleed/PrompyAI/blob/main/packages/mcp-server/src/utils/telemetry.ts)). It reads the session for context and reports no trend.

The claim fails as a general statement. **JevPromptCoach describes itself as a tool that "scores how well you write prompts to a coding agent, and shows whether your habits are improving"**, with a hit rate per check, a 30-day trend and "one habit to work on. Not seven." ([GitHub](https://github.com/CrowdLinker/JevPromptCoach)). Prompt-sensei is a "quiet, local-first prompt coach" for Claude Code and Codex with a report of repeated gaps and one "Next habit" ([GitHub](https://github.com/chengzhongwei/Prompt-sensei)). code-insights computes a weekly synthesis and an "AI Fluency Score" from four harnesses ([GitHub](https://github.com/melagiri/code-insights)); ctxray offers `style --trends` and a weekly digest over seven harnesses with no model call ([README](https://raw.githubusercontent.com/ctxray/ctxray/main/README.md)); tuneloop identifies "Agent re-work / re-steer themes" and "Patterns of deviations from best practices" across sessions ([GitHub](https://github.com/tuneloop/tuneloop)). The two closest to the proposal are also the newest and least used: agentic-coach (no stars, no licence, pushed four days before this report) keeps 30-day trends and checks whether earlier advice was followed ([GitHub](https://github.com/hkdeven/agentic-coach)), and agent-coach-cli (version 0.1.0, released 13 November 2026) scores eleven habits per conversation and keeps a run history ([PyPI](https://pypi.org/project/agent-coach-cli/)). The vendors are in the same space: Claude Code `/insights` writes a report on up to 200 recent sessions and their friction points ([Claude Code docs](https://code.claude.com/docs/en/costs.md)), and Copilot CLI `/chronicle` has `tips` and `improve` subcommands ([GitHub docs](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/chronicle)).

**The narrower claim that survives is about durability and follow-up, not about longitudinal analysis as such.** Three things appear unoccupied in the tools read. The first is coaching on behaviour beyond prompt text, delivered as a continuing programme that checks whether a specific habit changed; tuneloop and `/insights` detect such patterns and report them once, and only agentic-coach follows up. The second is habit state that outlives the harness's own retention without holding raw prompts: the `/insights` report and the transcripts it reads are deleted after `cleanupPeriodDays`, 30 days by default ([Claude Code docs](https://code.claude.com/docs/en/costs.md)), and Prompt-sensei's hash-only capture is the nearest existing answer. The third is a default that is local in the strict sense. "No cloud" in these tools usually means that the tool's own scripts make no network calls while the judgement still runs on a hosted model; Jev sends redacted prompts to a third-party API, and PrompyAI, CodeBurn and code-insights ship telemetry that the user must turn off.

The vendor feature is the comparison a user will make first, and its public defects are specific. `/insights` has attributed tool calls to the user ([issue 23230](https://github.com/anthropics/claude-code/issues/23230)), counted subagent sessions as the user's, suggested snippets that reference paths that do not exist, and cannot be scheduled ([issue 108210](https://github.com/anthropics/claude-code/issues/108210)). Its tokens count against the user's plan ([Claude Code docs](https://code.claude.com/docs/en/costs.md)). An independent review exists ([Nate Meyvis](https://www.natemeyvis.com/claude-codes-insights/)), and Cursor users have asked for an equivalent ([Cursor forum](https://forum.cursor.com/t/add-insights-like-in-claude-code/151047)), which is evidence of demand and of a gap on other harnesses. Two design ideas recur independently and are worth noting because nobody copied them from anybody: Jev and Prompt-sensei both restrict the report to one habit at a time, and Prompt-sensei and agentic-coach both state that scores are signals, not grades ("a coaching signal, not an objective grade"; "Corrections, repeated prompts, and 'unrelated tasks' are heuristics").

## The comparable tools show which parts of the proposal break in practice

The hybrid shape in the proposal, a deterministic pass followed by a small model judgement, is the design the newest tools converge on, and it is the shape of the agent-caddie pipeline, where the coach runs after the rule engine inside a detached finalizer and cannot change the deterministic findings ([flows](/docs/architecture/flows.md)). claude-reflect captures corrections by regex on every prompt and defers model validation to a command the user runs ([README](https://raw.githubusercontent.com/BayramAnnakov/claude-reflect/main/README.md)); agent-coach-cli makes one judge call per conversation with an offline heuristic as fallback; retro pairs a stdlib scanner with a model judgement ([GitHub](https://github.com/craftwork-design/retro)). The disagreement between the proposal and the field is in the mechanics underneath that shape.

**No tool was found that runs a model analysis from a process detached at `SessionEnd`, so this part of the proposal is unproven in the field.** The hook contract explains why it is delicate. `SessionEnd` has a default budget of 1.5 seconds, its output is discarded, and "Timeouts set on plugin-provided hooks don't raise the budget"; `Stop` does not run on a user interrupt and the transcript may lag behind it; a hook with `async: true` is killed when a `claude -p` session tears down, and the documentation's advice is to "start a fully detached process from it"; a background child must redirect its stdio or the hook waits for it ([hooks reference](https://code.claude.com/docs/en/hooks)). Node requires stdio that is not connected to the parent for a detached child to outlive it, creates a console window for detached children on Windows unless `windowsHide` is set, and gains nothing from `nohup`, which the proposal names and which does not exist on Windows ([Node.js](https://nodejs.org/api/child_process.html)). vibe-log-cli is the one tool that spawns a detached process from a hook and calls a model from it, and it does so on `UserPromptSubmit`, not at session end ([spawn helper](https://github.com/vibe-log/vibe-log-cli/blob/HEAD/src/utils/spawn.ts)). The failures on record come from claude-mem, which starts a long-lived daemon from `SessionStart`: its summary step was cancelled at session end with "0 out of 35 sessions ever completing" ([issue 1486](https://github.com/thedotmack/claude-mem/issues/1486)), and its tracker holds orphaned processes, stale PID files and several Windows-specific failures ([ProcessManager source](https://github.com/thedotmack/claude-mem/blob/HEAD/src/services/infrastructure/ProcessManager.ts)). Those are failures of a daemon, not of a one-shot child, and agent-caddie already plans a one-shot `caddie finalize` with a session lock and orphan catch-up; the evidence bears on the daemon option more than on the existing design.

**SQLite written from concurrent hook processes has a documented failure history, and the proposal's storage choice cannot meet the current runtime floor.** claude-mem silently dropped writes while `busy_timeout` was 0 ([issue 2821](https://github.com/thedotmack/claude-mem/issues/2821)) and has reports of WAL corruption with concurrent sessions ([issue 3179](https://github.com/thedotmack/claude-mem/issues/3179)); SQLite in WAL mode allows one writer at a time and the default busy timeout is zero ([SQLite forum](https://sqlite.org/forum/forumpost/c46e24c7c7?t=c)). The built-in `node:sqlite` module arrived in Node 22.5.0, needs no flag from 22.13.0, gained its `timeout` option in 22.16.0 and is a release candidate from 25.7.0 ([Node.js](https://nodejs.org/api/sqlite.html)); better-sqlite3 is a native addon ([GitHub](https://github.com/WiseLibs/better-sqlite3)), and sql.js keeps the database in memory and rewrites the whole file ([GitHub](https://github.com/sql-js/sql.js)). The design's leaning is Node 18 or later, one committed CJS bundle and no runtime dependencies ([design spec](/docs/specs/2026-11-11-agent-caddie-design.md)), and none of the three SQLite routes fits all three constraints. Node 18 and 20 are themselves end-of-life ([Node.js](https://nodejs.org/en/about/previous-releases)), which is a fact about the floor, not about SQLite.

**"The user's existing auth" is the weakest phrase in the proposal, for policy, cost and safety reasons.** Anthropic's legal page says OAuth authentication is "intended exclusively" for ordinary use of Claude Code, that developers may not "route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users" nor "collect, store, or intermediate Claude.ai credentials or session tokens", and that enforcement can come "without prior notice"; the same page does not prevent "an end user from signing in to the unmodified Claude Code binary with their own Claude subscription" ([legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). A plugin that spawns the unmodified `claude -p` sits between those two statements, and the research found no Anthropic statement on that case. The route is also moving: `--bare` never reads OAuth and "will become the default for `-p` in a future release" ([headless docs](https://code.claude.com/docs/en/headless)), and when `ANTHROPIC_API_KEY` is present, `-p` always uses it ([authentication docs](https://code.claude.com/docs/en/authentication)), so "existing auth" can silently mean metered API billing. On cost, claude-mem's background observer on a Max 20x plan "spent the next 7+ hours on that session's backlog" ([issue 5023](https://github.com/thedotmack/claude-mem/issues/5023)). On safety, a `SessionEnd` hook that ran `claude -p` produced "373 root sessions created within the most recent hour", because the child session fired the same hook ([issue 47871](https://github.com/anthropics/claude-code/issues/47871)).

The prompt path is where the most relevant maintainer has already changed his mind. The proposal's synchronous layer runs regex and token checks on each prompt. The maintainer of the severity1 plugin built a regex pre-filter of that kind and removed it, writing that "Pre-emptive intervention based on prompt text alone produces false positives whose cost (broken flow, eroded trust) exceeds the marginal token savings" and that this "rules out the entire 'detect X in prompt → intervene' family"; six detector ideas were closed, correction loops among them ([issue 26](https://github.com/severity1/claude-code-prompt-improver/issues/26)). That finding is about intervening at prompt time, not about measuring at prompt time. JevPromptCoach's default hook "appends one line to a local JSONL log and exits 0" in 27 to 31 ms ([GitHub](https://github.com/CrowdLinker/JevPromptCoach)), which matches what agent-caddie plans: compute heuristics, journal them, discard the text, and decide nudges from the previous turn's statistics ([flows](/docs/architecture/flows.md)). Two contract details matter for any prompt-time rule: `UserPromptSubmit` also fires for scheduled tasks, subagent reports and cross-session messages, so not every event is a human prompt, and exit code 2 blocks the prompt ([hooks reference](https://code.claude.com/docs/en/hooks)), which Jev notes "erases what you typed".

## Two of the five metrics have support, two need reframing and one has none

The published data sets are large enough to test the proposal's metrics against base rates, though none tests them as predictors of outcome. Anthropic's expertise study covers about 400,000 Claude Code sessions ([Anthropic](https://www.anthropic.com/research/claude-code-expertise)), SWE-chat about 18,000 public sessions ([SWE-chat](https://arxiv.org/html/2604.20779)), and a study of misalignment 20,574 sessions ([Tang et al.](https://arxiv.org/abs/2605.29442)). Almost all outcome labels in these studies are themselves model judgements, and the expertise classifier in the Anthropic study uses framing precision, verification requests and who corrects whom as inputs, so its finding that experts succeed more often is partly circular as evidence for metrics built on the same features.

| Metric in the proposal | Evidence for | Evidence against or main false positive | Computable without a model | Nearest thing in the design |
|---|---|---|---|---|
| Correction loop ratio | Anthropic's rule on two failed corrections | pushback follows about 46% of prompts; most misalignment is attributed to the agent | counting yes; "same issue" and cause no | rule `prompting.correction-streak` |
| Verification spec rate | all three vendors; expertise study | checks can live in configuration; exploratory prompts need none | yes, at session level | heuristic "verifiable check present" |
| Context bloat and drift | cost guidance; multi-turn degradation studies | no vendor threshold; typical sessions have 4 to 5 user turns; `/compact` is itself costly | cost signals yes; "unrelated domain" no | rule `cache.cold-compaction`; `/clear` and `/compact` events |
| Micromanagement index | none found | collaborative sessions are cheapest; experienced users interrupt more | no | none |
| Grounding precision | Anthropic, OpenAI and Cursor guidance | vendors say the agent can find files itself; exploration | yes, by regex on the first prompt of a task | heuristic "path present" |

**The correction ratio measures something normal.** In SWE-chat, users push back after about 46% of prompts and that rate is roughly stable across working modes ([SWE-chat](https://arxiv.org/html/2604.20779)). In the misalignment study the leading causes are the agent failing to follow instructions (36.49%) and an undeterminable cause (26.85%), with underspecified instructions at 15.36%; of the episodes with a visible resolution, 91.49% needed explicit developer pushback ([Tang et al.](https://arxiv.org/abs/2605.29442)). A raw ratio therefore mostly records the agent's errors and the user doing the right thing about them. The only numeric threshold any vendor publishes is Anthropic's: after two failed corrections, run `/clear` and write a better prompt instead of a third ([best practices](https://code.claude.com/docs/en/best-practices)). The design's existing rule `prompting.correction-streak` is close to that form. Deciding that two corrections target the same issue, and who caused it, is a judgement; the cause axis was the least reliable in the misalignment study, with human agreement of 0.65 and model accuracy of 0.72.

**Verification has the best support of the five and is measured in the wrong place if measured per prompt.** Anthropic's guidance is to "Give Claude something it can run that comes back pass or fail", and it lists `CLAUDE.md`, `/goal`, a `Stop` hook and a review subagent as places the check can live ([best practices](https://code.claude.com/docs/en/best-practices)); OpenAI's equivalent is a "Done when" statement ([Codex best practices](https://developers.openai.com/codex/learn/best-practices)). In the expertise study, verified success is 15% for novices against 28 to 33% for others ([Anthropic](https://www.anthropic.com/research/claude-code-expertise)). Because the check can live in configuration, a per-prompt rate penalises users who set verification up once; the session-level question (did a check run before the work was accepted) avoids that. The main false positive is exploratory work: 18.2% of prompts in SWE-chat ask to understand existing code, and Anthropic calls a vague prompt "completely fine" when exploring.

**The context metric has evidence for cost, weak evidence for quality and none for its threshold.** No vendor states a turn count. A typical session in the Anthropic study has about four user turns and the median for Claude Code in the misalignment study is five, so a threshold of 15 to 20 turns describes the tail. Anthropic has retired "The context window is your main constraint, manage it aggressively" as advice, on the grounds that "Most current models have a 1M-token window and compaction happens on its own, so running out is rare", while keeping that "`/clear` between tasks is still worth doing"; it also notes that `/compact` "is itself a big request" ([best practices](https://code.claude.com/docs/en/best-practices), [costs](https://code.claude.com/docs/en/costs)). Advice to compact can therefore raise cost, which is the case the design's `cache.cold-compaction` rule already covers. The quality side rests on laboratory results, a 39% average drop in multi-turn settings ([Laban et al.](https://arxiv.org/abs/2505.06120)) and Chroma's context-rot work ([Chroma](https://www.trychroma.com/research/context-rot)), and in the field context loss is the attributed cause of 4.30% of misalignment episodes. "Multiple unrelated file domains" requires task segmentation, which is a judgement and a prerequisite for every one of the five metrics.

**The micromanagement index has no evidence behind it and some against it.** No vendor warns against micromanagement; the nearest guidance concerns not supplying what the agent can find for itself, which is a different thing. Collaborative sessions in SWE-chat cost a median of $0.92 per 100 committed lines against $2.71 for sessions where the agent wrote nearly everything ([SWE-chat](https://arxiv.org/html/2604.20779)). Experienced users interrupt in about 9% of turns against about 5% for new users, and Anthropic describes this as active monitoring ([Anthropic](https://www.anthropic.com/research/measuring-agent-autonomy)). The top misalignment symptom is constraint violation at 38.33%, which is an argument for stating constraints, not for stating fewer. One finding points the other way: expert sessions average 12 agent actions per prompt against about 5 for novices ([Anthropic](https://www.anthropic.com/research/claude-code-expertise)), subject to the circularity already noted. A descriptive figure such as agent actions per user turn is computable; the index as a judgement of the user is not supported.

**Grounding has moderate support and a clear false positive.** Anthropic and OpenAI both advise pointing the agent at specific files, and Cursor puts the limit plainly: "if you know the exact file, tag it. If not, the agent will find it." ([Cursor](https://cursor.com/blog/agent-best-practices)). A regex for paths and symbols is workable and already planned as a prompt heuristic; it is meaningful only on the first prompt of a task, since later prompts inherit context. Research on underspecified tasks found that interaction improves results by up to 74% and that models struggle to tell underspecified instructions from complete ones ([Ambig-SWE](https://arxiv.org/abs/2502.13069)), which supports the behaviour and warns against asking a model to grade it.

What the list of five lacks most is an outcome. All five are properties of the user's input, and without a measure of how the session went, a coach cannot tell a harmless deviation from a costly one. The data sets suggest candidates that need no model: abandonment (19% of novice sessions against 5 to 7% for others), code survival into commits (59.4% in SWE-chat), cold-cache resumes, and a repeated correction that should have become a rule. The misalignment study found that misalignment in one session raises its probability in the next session in the same repository from 0.336 to 0.519, which is the best published evidence that anything about these sessions is persistent enough to coach over time.

## ADR-0018 has twelve decisions to make

The decisions below are listed in dependency order: the first two determine what the coach can know, the next four how it runs, and the rest what it says and how it is checked. Each sub-section states the options and the evidence. The current design text for the coach is short: off by default; after the deterministic pipeline, a redacted digest of "rule ids, metrics, risk level; never prompt text" goes to a configured provider under per-session, per-day and per-month USD caps metered from the journal; findings carry `confidence < 1`, the model and the prompt version ([design spec](/docs/specs/2026-11-11-agent-caddie-design.md), [overview](/docs/architecture/overview.md)).

| Decision | Current design leaning | Proposal under review | Other options seen in the field |
|---|---|---|---|
| 1. What the coach reads | redacted digest, no prompt text | session trajectories | digest plus bounded quotes read from the transcript |
| 2. Whether prompt text is stored | never by default; opt-in flag | raw `prompt_text` column | hashes only; redacted text |
| 3. Storage engine | append-only JSONL journal and JSON files | SQLite in WAL mode | JSONL spool in hooks with SQLite in the worker |
| 4. Provider and credentials | `provider-anthropic`, `provider-claude-cli`, `noop` | "the user's existing auth" | Agent SDK; local model; host-provided generation |
| 5. Budget unit | USD caps from pack pricing | not stated | call counts; CLI budget flags |
| 6. Trigger and process shape | inside the detached finalizer | worker spawned on `Stop` at a threshold | on demand; scheduled; daemon |
| 7. Work on the prompt path | heuristics only, text discarded | checks under 50 ms plus a raw log write | nothing on the prompt path |
| 8. Delivery | one lesson of 160 characters or fewer, rare `systemMessage`, report | top unshown tip at session start | one habit at a time; status line |
| 9. What the model adds | not specified | scores the five metrics | explain and rank deterministic findings only |
| 10. Validation of findings | `confidence < 1`, prompt version | not stated | evidence quotes, second pass, labelled sample |
| 11. Safety guards | provider error yields no finding | not stated | recursion guard, transcript as untrusted data |
| 12. Portability | `LlmProvider` port, capability gating | Claude Code only | per-harness providers |

### 1. What the coach reads

The options are the digest as specified (rule identifiers, metrics and risk level), the digest plus a bounded set of quoted turns read from the transcript at coaching time and not stored, and the raw transcript or a large part of it. Reading and storing are separate questions: the harness already keeps the transcript for 30 days by default, so the coach can read text that agent-caddie never writes to its own store.

The evidence for more context is the validation result in the misalignment study. **A single extraction pass kept only 53.9% of its findings after validation (16,118 of 29,896), and of the invalid ones 57.72% came from observational blind spots and 42.28% from normative prior bias**, meaning the model flagged a deviation from its idea of good practice when nothing had gone wrong ([Tang et al.](https://arxiv.org/abs/2605.29442)). A digest of rule identifiers and metrics removes the material a model would need to avoid both errors, so a digest-only coach should be expected to produce a higher rate of unsupported findings. That is an inference; no study compares judge accuracy on raw against redacted input. A digest-only coach is also limited to explaining and ranking what the rules already found, which bears on decision 9.

The evidence for less context is the privacy position of the field and of the design. Claude Code's own telemetry redacts the prompt attribute unless `OTEL_LOG_USER_PROMPTS=1` is set ([monitoring docs](https://code.claude.com/docs/en/monitoring-usage)). Jev offers `redact` and `metadata_only` levels. Anthropic's Clio is the reference design for analysis that keeps raw conversations away from readers ([Anthropic](https://www.anthropic.com/research/clio)). Sending prompt text to a provider is also the point at which "local-only" stops being literally true, and the design's network decision is local-only with the coach as the stated exception.

### 2. Whether prompt text is stored

The options are never (the current default, with tests that assert no prompt text reaches the store, journal or bundle), opt-in through the existing `privacy.storePromptText` flag, redacted or hashed text, and raw text by default as in the proposal's `turns.prompt_text` column.

Prior art splits. Prompt-sensei states "raw prompts are never stored" and keeps hashes; agentic-coach keeps a ledger with "no prompt text"; Jev redacts by default. claude-mem stores raw prompts locally and offers `<private>` tags; code-insights and tuneloop parse sessions into local databases. The tools that market themselves as coaches chose not to store; the tools that store are memory and analytics products. The argument for storing is that longitudinal analysis otherwise loses its source after the harness's retention window, and that any later change to a metric or rubric cannot be applied to old sessions. agent-coach-cli states the consequence directly: "Changing the rubric means earlier runs have no scores for new habits" ([PyPI](https://pypi.org/project/agent-coach-cli/)). The argument against is that raw storage contradicts a stated goal of the design and would need the shareable-bundle redaction and the tests to change with it. A middle position exists in the design already: store heuristics and findings durably, and accept that re-scoring is possible only within the transcript retention window.

### 3. Storage engine

The options are the JSONL journal and JSON documents as designed, `node:sqlite` with the Node floor raised to 22.13 or later, a bundled native or WebAssembly SQLite, and a split in which hooks append to a JSONL spool and only the detached process opens a database.

The proposal's three tables map onto structures the design already has: `sessions` onto `sessions/<id>.json` and `index.jsonl`, `turns` onto `prompt_heuristics` journal events, and `coaching_insights` onto findings with `category: coaching` plus `lesson.json` ([overview](/docs/architecture/overview.md)). The case for SQLite is query convenience for trends over many sessions, and several comparable tools use it. The case against is the failure history in the previous section, the Node floor, and the fact that a hook process is short-lived and concurrent with other sessions, which is the pattern that produced claude-mem's dropped writes and WAL corruption; agentsview avoids that by letting one daemon own the file ([GitHub](https://github.com/kenn-io/agentsview)). The design already accepts a higher floor in one place: the planned OpenCode adapter uses `node:sqlite` and raises that adapter's floor to 22.5 while the kernel stays on 18 ([harness lifecycles](/docs/architecture/harness-lifecycles.md)). Two facts are missing for this decision: a cold-start cost for opening `node:sqlite` in a hook, and a sourced guarantee for atomic appends to JSONL from concurrent processes.

### 4. Provider and credentials

The options are an API key through `provider-anthropic`, the signed-in CLI through `provider-claude-cli`, the Agent SDK, a local model, and generation provided by the host harness.

The API key route has clear billing and clear terms, and requires the user to have a key, which many subscription users do not. The CLI route needs no key and is what agent-coach-cli does with the signed-in `claude` or `codex` binary; it carries the policy ambiguity, the `--bare` change and the `ANTHROPIC_API_KEY` precedence described earlier, and each call starts a full Claude Code session whose token overhead this research did not measure. `claude -p` does support `--output-format json` with `total_cost_usd`, `--json-schema` and `--max-budget-usd` ([headless docs](https://code.claude.com/docs/en/headless)), which gives the CLI route a way to report and bound spend. The Agent SDK is what claude-mem and vibe-log-cli use; from 7 October 2026 Max, Ultra and Team plans include monthly API credits for it ([Claude support](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)), and it would be a runtime dependency. A local model through Ollama is offered by code-insights and tuneloop and is the only option that keeps the strict local-only property; no evaluation of small or local models as judges of this kind was found. Host-provided generation exists on OpenCode as `ctx.experimental.generate.text` ([OpenCode docs](https://opencode.ai/docs/build/plugins/server)) and on no other harness examined.

Model price is no longer the constraint it was. Claude Haiku 5.5 costs $0.10 per million input tokens and $0.50 per million output tokens for prompts up to 100,000 tokens, against $1 and $5 for Haiku 4.5 ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)). On an assumed digest of 8,000 input and 800 output tokens, that is about $0.0012 per session on Haiku 5.5 and $0.012 on Haiku 4.5; the token counts are an assumption of this research, not a measurement.

### 5. Budget unit and metering

The options are USD caps computed from pack pricing as designed, the CLI's own `--max-budget-usd` and reported `total_cost_usd`, caps on the number of coach calls, and a gate on session size such as the planned `minSessionCostUsd`.

USD caps metered from the journal work as specified on the API key route. On the subscription route, a call draws from plan limits and not from a dollar balance ([Claude support](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)), so a USD cap is an estimate of something the user does not pay in dollars, and the harm to bound is quota exhaustion, as in the claude-mem report. agent-coach-cli bounds its judge by count (one call per conversation, `--max-sessions`, and a `scan` dry run) instead of by money. No tool publishes a per-session dollar cost; the public figures are tuneloop's $6.92 for 118 sessions with a Haiku and Sonnet pair ([GitHub](https://github.com/tuneloop/tuneloop)) and Jev's $0.06 to backfill 1,039 prompts, which differ by two orders of magnitude per unit because they analyse different things.

### 6. Trigger and process shape

The options are the coach as a step inside the existing detached finalizer (the current flow), a separate worker spawned from `Stop` when a threshold is met (the proposal), an on-demand command, a scheduled task, and a long-lived daemon.

The finalizer option reuses a session lock, a wait for transcript stability and orphan catch-up that the design already has, and runs once per session. The `Stop` option gives feedback during a long session, at the cost of a trigger that fires every turn, does not fire on interrupt and can precede the transcript write ([hooks reference](https://code.claude.com/docs/en/hooks)); it also needs its own once-per-session guard. On-demand and scheduled runs are what the closest tools chose: claude-reflect defers its model pass to `/reflect`, agentic-coach uses scheduled daily and weekly tasks "instead of a hook worker", and `/insights` is a command. Those choices avoid every detached-process failure listed earlier and put the cost under the user's hand; they also mean coaching happens only when the user remembers it, which is the opposite of a continuing programme. The daemon option has the worst record in the evidence. Detached spawn from a hook on Windows was not tested in this research.

### 7. Work on the prompt path

The options are the current plan (compute heuristics, journal them, discard the text, within a 300 ms budget that includes Node start-up), the proposal's additional synchronous checks and raw log write within 50 ms, and no prompt-time work at all, with heuristics derived from the transcript afterwards.

The 50 ms figure and the 300 ms budget are not comparable as written, because the first reads as a budget for the checks and the second includes process start. Jev's measured 27 to 31 ms shows that an append-and-exit hook can be fast; no sourced measurement of Node start-up inside a Claude Code hook was found, and the debug `Hooks:` duration lines that would provide one exist only from v2.1.296. The severity1 reversal is evidence against acting on prompt text at prompt time, and is silent on measuring. The transcript-only option removes the hook from the critical path and loses the prompt event on harnesses with no usable transcript, such as Cursor ([harness lifecycles](/docs/architecture/harness-lifecycles.md)).

### 8. Delivery surface and cadence

The options are the single lesson at session start, a `systemMessage` to the human during the session, the status line, the session report, and a periodic report in the style of the other coaches. The proposal's "inject the top unshown tip at `SessionStart`" matches the planned lesson mechanism, including the rule against repeating a lesson shown in the last N sessions.

Two facts complicate the lesson as a channel for coaching the human. `SessionStart` output through `additionalContext` goes into the model's context, with a cap of 10,000 characters ([hooks reference](https://code.claude.com/docs/en/hooks)), so a tip delivered that way reaches the model first and the person only if the model repeats it; whether a `systemMessage` returned from `SessionStart` is shown to the user was not tested. The field's independent convergence on one habit at a time supports the single-lesson limit. Follow-up is the feature only agentic-coach has, and it depends on findings having stable identifiers across sessions, which model-generated findings do not have unless the design gives them one. Tone has a public data point: users have asked `/insights` to report neutrally. The impact tracker's minimum sample of five sessions is the existing mechanism that could carry follow-up for coaching findings.

### 9. What the model is asked to add

The options are to have the model explain and rank deterministic findings, to have it make the judgements that rules cannot (whether corrections target the same issue, where a task begins and ends, what caused a misalignment), and to have it score behaviours directly as the proposal's five metrics imply.

The metrics section shows which parts are deterministic: verification at session level, grounding on a first prompt, cost signals and counts. The judgements that need a model are the ones with measured error rates, 0.72 accuracy on cause and 0.84 on symptom in the misalignment study. The mitigation with evidence behind it is to require an observable harm signal (pushback, rework, a failed check, abandonment) before a behaviour is reported as a problem, which counters normative prior bias. The AGENTS.md study is a caution about the output side: adding context files produced no gain in task success and more than 20% more cost ([AGENTS.md study](https://arxiv.org/abs/2602.11988)), so advice that ends in "add this to your instructions file", as claude-reflect and code-insights produce, is not free.

### 10. Validation of coach output

The options are the current fields alone (`confidence < 1`, model, prompt version), deterministic checking of verbatim evidence quotes against the transcript, a second validation pass, and a human-labelled sample as a release gate.

The misalignment study's method is the best documented: a pinned judge at temperature 0, verbatim quotes with turn numbers, a second pass that removed 46% of first-pass findings, and precision of 0.93 on 200 human-checked records ([Tang et al.](https://arxiv.org/abs/2605.29442)). Quote checking needs the coach to read text (decision 1) and costs nothing at run time; a second pass doubles the calls (decision 5). The design plans promptfoo for evals; its `llm-rubric` default grader depends on which credentials are present, so the grader must be pinned and a `threshold` set for results to be reproducible ([promptfoo](https://www.promptfoo.dev/docs/configuration/expected-outputs/model-graded/llm-rubric/)). The METR result that developers were 19% slower while believing they were 20% faster ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)) is a reason not to validate coaching by asking users whether it helped.

### 11. Safety guards

The matters to settle are recursion, untrusted input and failure handling. For recursion, the 373-session incident shows what happens without a guard; the documented means are an environment variable owned by the tool together with `--settings '{"disableAllHooks": true}'` on the child, and Claude Code sets `CLAUDECODE=1` and `CLAUDE_CODE_CHILD_SESSION=1` in hook commands ([plugin hints](https://code.claude.com/docs/en/plugin-hints.md)); vibe-log-cli carries its own guard ([source](https://github.com/vibe-log/vibe-log-cli/blob/HEAD/src/lib/prompt-analyzer.ts)). Whether `disableAllHooks` also disables plugin hooks was not confirmed. For untrusted input, a transcript contains tool output and web content, and agentic-coach states the rule: "Nothing written in a transcript is ever followed as an instruction." A digest-only coach has little exposure here; a coach that reads text has all of it. For failure handling, claude-mem parsed a quota-limit message as invalid output and entered a respawn loop ([issue 3037](https://github.com/thedotmack/claude-mem/issues/3037)); the design's rule that any provider error yields no finding and a journal entry addresses that case if retries are also bounded.

### 12. Portability across harnesses

The options are to specify the coach against the `LlmProvider` port only and leave credentials to each provider adapter, or to specify a Claude Code route first and generalise later. The design's capability matrix says the coach needs nothing beyond deterministic findings, which holds for a digest-only coach and stops holding if the coach reads transcript text, since `hasTranscript` is false on Cursor.

Session end is short everywhere: Codex CLI gives `SessionEnd` one second by default and requires hooks to be trusted through `/hooks` ([Codex docs](https://learn.chatgpt.com/docs/hooks)), Gemini CLI does not await it ([Gemini CLI docs](https://geminicli.com/docs/hooks/reference/)), and Cursor's is fire-and-forget ([Cursor docs](https://cursor.com/docs/agent/hooks)), so a detached process or catch-up is the common denominator. Cursor and Copilot CLI both load Claude Code hook configuration ([Copilot docs](https://docs.github.com/en/copilot/reference/hooks-configuration)), which makes a Claude Code plugin's hooks fire in harnesses it was not written for, and a `claude -p` provider would then run from a session that is not Claude Code. Gemini CLI's consumer service ended on 18 June 2026 in favour of Antigravity CLI ([Google](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)), whose hook contract was not verified. The headless modes and credential terms of the other harnesses were not researched.

## What the research could not verify

On the tools: no Reddit or Hacker News discussion was retrieved, so user sentiment rests on issue trackers and one review. Several small tools were read only from listings. How PrompyAI triggers its scoring automatically is unconfirmed. The internals of `/insights` are known only second-hand ([community guide](https://raw.githubusercontent.com/FlorianBruniaux/claude-code-ultimate-guide/693d97d284ea342c8c8fb13894df0cee26d3a3d3/docs/resource-evaluations/zolkos-insights-deep-dive.md)): the primary article was unreachable, the model it uses is reported inconsistently, and a reported cap of 50 sessions conflicts with the official figure of 200. Whether Cursor, Codex or Gemini have native equivalents of `/insights` was not verified. No tool publishes evidence that its users' habits improved, and no tool publishes a per-session cost.

On policy and billing: no Anthropic statement was found on a plugin that spawns `claude -p` in the background, and the Consumer Terms were not read. The article on Agent SDK billing was read through a summarising fetch, so its wording is not quoted here beyond the dates and plan names.

On mechanics: the token overhead of a non-bare `claude -p` call was not measured. Whether `disableAllHooks` covers plugin hooks, and whether a flag exists to stop the child session persisting a transcript, are unknown. Detached spawn from a hook on Windows was not tested. No benchmark was found for `node:sqlite` cold start, WAL mode through `node:sqlite` was not verified, and the atomic-append behaviour of JSONL under concurrent writers is unsourced. Hook latency figures other than Jev's are anecdotal and are left out of this report. Whether a `systemMessage` from `SessionStart` is shown to the user needs a test.

On evidence: no study regresses a session outcome on prompt features, so none of the five metrics is validated as a predictor. No study compares judge accuracy on raw against redacted input, and none evaluates small or local models as judges of developer behaviour. No study measures whether coaching changes how developers work with agents; the nearest is work on code-review nudges at Meta, which was seen only as a search summary ([ACM](https://dl.acm.org/doi/abs/10.1145/3540250.3549104)). A later METR update exists and was not analysed in depth ([METR](https://metr.org/blog/2026-02-24-uplift-update/)).

## Conclusion

The proposal and the design disagree less than the four tensions suggest, because three of them reduce to one question: whether the coach is allowed to read prompt text. If it is not, the digest-only design stands, storage stays as it is, and the coach is a ranking and explanation step whose value over the deterministic rules is small and whose error rate should be expected to be high. If it is, reading can still be separated from storing, since the harness keeps the transcript for 30 days, and the evidence on quote checking and second-pass validation becomes usable. The storage engine and the prompt-path questions then follow from that answer and from the Node floor, not from coaching itself. The auth question is independent and is the one where the outside world can change the answer without notice.

The research also changes what the differentiator is. Longitudinal analysis is common; what is rare is a record that outlasts the harness's retention without holding prompts, a check on whether earlier advice was followed, and a coach that stays silent unless something observable went wrong. The first two already exist in the design as the journal and the impact tracker, built for rules and not yet for coaching findings. The third is absent from the proposal's five metrics, all of which describe the user's input and none the session's outcome, and it is the gap the published evidence most directly speaks to.
